Adding a category without breaking production

A trained shortcut and a changing list of options are a dangerous mix. What goes wrong, the rule shad0w follows now, and the lifecycle of an option from rename to retirement.

Gaurav Chauhan2026-10-083 min readproductionlifecyclesafetyrelease notes

Every intent classifier meets the same Tuesday. Product adds a new intent, say transfer, to the list the LLM chooses from. The LLM handles it beautifully from the first request: it reads the new option in its prompt and uses it.

Now imagine a learned shortcut in front of that LLM, trained last week on the old list. What does it do with "send 50 to my sister"?

What goes wrong#

It answers. A table trained on refund, lost_card and balance has never seen a transfer. It cannot say "I don't know this option". It can only pick its closest match, and it may pick it with high confidence.

We tested exactly this before shad0w 0.3.1. Here is what happened on the new option's messages:

  • Added option: more than half went out with a wrong, old label, while marked certified.
  • Removed option: every message about it went out with the deleted label.

The certificate was not lying about the world it was computed in. The world changed under it.

The rule#

Since 0.3.1, shad0w compares the options you offer now with the options the table learned, on every load. In the proxy, it compares them on every request. The rule is short:

The table only answers with options it learned, from a list you still offer, under the certificate it was given.

That plays out as follows.

You add an option. Every decision goes to your LLM, flagged options_changed, until you retrain. Not just the new option's messages: all of them. The table cannot tell which messages belong to the new option, and its certificate was earned without it. Nothing is wasted in the meantime. Your LLM's answers, including the new label, keep flowing into the log, and the next train() learns the full list.

You remove an option. The table keeps serving everything else. If it would answer with the removed option, that decision goes to your LLM instead, flagged option_removed. Removing an option does not change what your LLM says about the others, so their certificate still stands.

You rename an option. Nothing needs retraining. A rename changes the label, not the decision:

intent = shad0w.decision("intent", options=["refund", "card_lost", "balance"], llm=...,
                         rename={"lost_card": "card_lost"})

The table answers card_lost straight away. The next training run rewrites the old name in the log as it reads it, so no history is lost.

You retrain. The table learns the current list, gets a new certificate, and serves again. The automatic retrain gate, which normally keeps an old table unless the new one is at least nearly as good, steps aside here. A table for a different list of options is no baseline.

Why not keep serving the old options?#

It is tempting. Most messages are not about the new option, so most of the table's answers are still right. That is why the option exists: on_new_option = "serve".

It is not the default, for one reason. The table cannot tell you which of its answers were really about the new option. Those come back confident and wrong, and nothing downstream knows. A burst of LLM calls for a day costs money. Silent wrong answers cost trust. We default to spending the money.

The same in every runtime#

The JavaScript package follows the same rules (optionsAdded, optionsRemoved, rename, onNewOption). The proxy applies them to the options each Decisions API request lists. And the new Changing your options page covers merging, splitting and checking where you stand.
