Decisions API & System One: zero code#

Two kinds of API already describe a decision completely in every request: the question's name and its finite list of answers.

  • OpenAI's Decisions API: POST /v1/decisions, model gpt-6-luna, in public beta since 6 Oct 2026. Question types choice, predicate (yes/no) and score.
  • System One decision models: TypeSafe's Jev, and the open Kev, Laya, Julia, Clef and others. They all speak POST /v1/systemone, with question types choice, noul (yes/no) and score.

Because the request already says what is being decided, shad0w proxy needs no header and no marking. You move base_url, and nothing else.

OpenAI Decisions API#

shad0w proxy --upstream https://api.openai.com/v1      # dashboard at http://localhost:8010

from openai import OpenAI                                # openai >= 3.26

client = OpenAI(base_url="http://localhost:8010/v1")     # the only change
d = client.decisions.create(
    model="gpt-6-luna",
    input="my card was stolen yesterday",
    questions=[{
        "type": "choice", "name": "intent", "instructions": "Which support intent is this?",
        "choices": [{"value": "lost_card", "description": "card lost or stolen"},
                    {"value": "refund", "description": "wants money back"},
                    {"value": "other", "description": "anything else"}],
    }],
)

The response has the same shape whether OpenAI or the table answered it: an answers list with choice, confidence and probabilities for each question. Table answers also carry a shad0w object (source, certified, flag), and every response has an x-shad0w-source header: table, teacher or mixed. Your API key is forwarded to OpenAI as usual, or set --api-key-env OPENAI_API_KEY on the proxy.

System One servers (Jev, Kev, Laya, ...)#

Point the proxy at any server that implements /v1/systemone, then point your client at the proxy:

shad0w proxy --upstream http://127.0.0.1:8081/v1         # the System One server's base URL

import requests

r = requests.post("http://localhost:8010/v1/systemone", json={
    "model": "kev",
    "state": "my card was stolen yesterday",
    "questions": {
        "intent": {"type": "choice", "instructions": "Which support intent is this?",
                   "criteria": {"lost_card": "card lost or stolen", "refund": "wants money back", "other": "anything else"}},
        "urgent": {"type": "noul", "instructions": "Is it urgent?"},
    },
}).json()
r["answers"]["intent"]["choice"], r["answers"]["urgent"]["noul"]

Run an open decision model on your laptop. llama.cpp serves the System One endpoint for the open GGUF builds (Kev 0.8B/4B/9B, Laya, Julia-1, Clef-Flash, Nimble, OpenJev and lev from ggml-org on Hugging Face):

llama-server -hf ggml-org/Kev-0.8B-GGUF --port 8081      # then: shad0w proxy --upstream http://127.0.0.1:8081/v1

This exact setup was tested end to end on an Apple-silicon Mac with shad0w 0.3.0 and llama.cpp 0.6.0. Ollama's library also lists decision models such as laya, tev1, nimble and clef-flash, served at /v1/systemone from Ollama 0.40; that route was not tested here.

llama.cpp implements /v1/systemone but not /v1/decisions. A Decisions-API request the table cannot answer is forwarded upstream, so against llama.cpp it comes back as the server's 404, unchanged.

What gets saved, exactly#

For each request, every choice and yes/no question goes to the table first.

  • All of them certified: the proxy answers by itself. No upstream call, no tokens, microseconds.
  • Some certified: only the remaining questions are sent upstream, in one request. The answers are merged back in the original order. You pay for the smaller request.
  • None certified: the request goes upstream as it is.

score questions always go upstream: shad0w does not learn ordinal scales. Every answer that came from upstream is logged per question, so shad0w train --dir shad0w can learn from it. Questions are created the first time their name is seen, with their options taken from the request.

Spot checks work as everywhere else: --audit-rate re-asks a share of table answers upstream in the background to measure live agreement.

To turn interception off for these endpoints, drop decisions from the capture list: --capture header,model,tools.

Use a decision model as the teacher#

You can also go the other way: let shad0w call a decision model directly, with no proxy, and learn from its answers.

import shad0w

intent = shad0w.decision(
    "intent",
    options={"lost_card": "card lost or stolen", "refund": "wants money back", "other": "anything else"},
    llm="systemone/kev",                       # or "openai-decisions/gpt-6-luna" (uses OPENAI_API_KEY)
    base_url="http://127.0.0.1:8081",          # the System One server; "/v1" is added when missing
)
intent("my card was stolen yesterday")         # Kev answers, the answer is logged
intent.train()                                 # later: the table answers the certified share itself

Yes/no questions (options={"type": "yesno", "instructions": "Is it urgent?"}) map to noul on System One and to predicate on the Decisions API. In JavaScript the same presets are llm: "systemone/kev" and llm: "openai-decisions/gpt-6-luna"; see JavaScript.

shad0w serve speaks both too#

A trained bundle served with shad0w serve --bundle shad0w/intent/bundle answers POST /v1/decisions and POST /v1/systemone from the table alone. Questions the bundle does not know, and score questions, come back with the flag unsupported; there is no LLM behind serve. See HTTP.

Is this worth it next to a decision model?#

Decision models are already fast and cheap, so the case is narrower than against a chat LLM:

  • The table answers in microseconds on your own CPU, with no network hop and no per-token price. A hosted decision costs about $0.030 per 1,000 at gpt-6-luna's list price, or $0.0126 with Jev.
  • It carries a written bound on how often it disagrees with the model it learned from.
  • It needs about 1,000 logged answers per question first, and it only answers the share it is certified on. The rest still goes to the decision model.

The comparison page puts numbers on this.
