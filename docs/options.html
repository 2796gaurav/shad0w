Changing your options#

Products change. You will add an intent, retire a team, or rename a label. A table that was trained and certified on the old list of options cannot be trusted with the new one, so shad0w notices the change and adjusts on its own.

The rule: the table only ever answers with options it learned, from a list you still offer, under the certificate it was given. Anything else goes to your LLM, and your LLM's answers keep being logged so the next training run learns the new list.

At a glance#

You… What the table does until you retrain Flag on deferred decisions
add an option Nothing. Every decision goes to your LLM. options_changed
remove an option Keeps answering with the options that remain. Never answers with the removed one. option_removed
rename an option (with rename=) Keeps answering, using the new name. —
retrain Learns the current list, gets a new certificate, and serves again. —

Adding an option#

intent = shad0w.decision("intent", options=["refund", "lost_card", "balance", "transfer"],   # "transfer" is new
                         llm="openai/gpt-4.1-mini")
intent.options_added      # ('transfer',)
intent("send 50 to my sister")
# Decision(answer='transfer', source='teacher', flag='options_changed', ...)   your LLM answered

Why everything goes to your LLM, and not only the new option's messages: the table cannot recognise a message about something it has never seen. It would label "send 50 to my sister" with its closest old option, possibly with high confidence. In our test, before this protection existed, a table served more than half of a new option's messages with an old label. The certificate was earned on a world without the new option, so it no longer covers any answer.

While you wait, nothing is wasted. Every LLM answer, including the new option, is logged. Once enough of them exist, retrain:

intent.train()            # learns all four options; serving resumes with a fresh certificate

auto_train does this for you. The retrain gate (retrain = "gated") never blocks this case: an old table that answers a different question is not a baseline for the new one.

Prefer to keep serving the old options anyway? on_new_option = "serve" keeps the table answering with what it knows, and only the new option's messages reach your LLM when the table happens to be unsure. That is a deliberate trade: the certificate no longer describes those answers. Use it only if a brief dip in agreement is cheaper than a burst of LLM calls.

Removing an option#

intent = shad0w.decision("intent", options=["refund", "lost_card"], llm=...)   # "balance" retired
intent.options_removed    # ('balance',)

Answers the table would give as balance go to your LLM (flag option_removed), which now picks among the options you still offer. Everything else keeps being served: removing an option does not change what your LLM says about the others. At the next train(), old log rows labelled balance are left out automatically.

Renaming an option#

intent = shad0w.decision("intent", options=["refund", "card_lost", "balance"], llm=...,
                         rename={"lost_card": "card_lost"})
intent("my card was stolen").answer      # 'card_lost', straight from the table, no retraining

A rename is the one change that needs no new certificate: the table's decisions are the same, only the name differs. The next train() rewrites the old name in the log as it reads it, so no history is lost. In shad0w.toml:

[questions.intent]
rename = { lost_card = "card_lost" }

From the command line: shad0w train --log log.jsonl --out bundle/ --rename lost_card=card_lost.

Merging and splitting#

  • Merge two options into one: rename both to the same new name and list only the merged name in options. The table answers with the merged name at once; retrain soon so the certificate describes the merged option.
  • Split one option into two: that adds at least one option, so the table defers until it relearns from your LLM's new answers.

Through the proxy#

With the OpenAI Decisions API or System One, each request lists its options, and the proxy compares them with the table's on every request. Add a choice in your request and that question goes to the upstream model until the table is retrained; your code changes nothing else. On the chat path, the options come from your JSON-schema enum, a forced tool's enum, or the X-Shad0w-Options header.

In JavaScript#

const intent = await decision("intent", { options: ["refund", "lost_card", "balance", "transfer"], llm: "openai/gpt-4.1-mini",
                                          bundle: "shad0w/intent/bundle", rename: { lost_card: "card_lost" } });
intent.optionsAdded     // ["transfer"]: every decision goes to the LLM until the bundle is retrained

onNewOption: "serve" is the JavaScript spelling of on_new_option = "serve".

Checking where you stand#

shad0w stats --log shad0w/intent/log.jsonl     # answers per option, and whether there are enough to train

intent.stats() reports options_added and options_removed; the dashboard shows the options_changed and option_removed flags with everything else. After adding an option, aim for at least 20 logged answers for it before retraining (shad0w warns below that). Until it has enough examples, the table rarely answers it, which is safe: those messages go to your LLM.
