Scale: options, size and speed#

Short answers:

  • Options: up to 1,024 per question.
  • Speed: stays in microseconds whatever the option count.
  • Size: grows with vocabulary × options. Cap it with max_mb.
  • Growth: the table does not keep growing on its own. Each training run replaces it.

Measured#

Synthetic traffic, so only the option count changes: each option has its own distinctive words, the teacher is perfectly consistent, and the same certifier runs everywhere. Measured on 12th Gen Intel(R) Core(TM) i7-1255U (12 threads), Linux-7.0.11-76070011-generic-x86_64-with-glibc2.39, 2026-10-08.

Synthetic traffic with one consistent teacher; α = 5%. Training time is wall clock on the machine below. The 500-option row: measured before the 0.3.1 size-budget fix (the K x K matrix was not counted), so it overshoots its 4 MB budget. Source: results/b9_scale.json.

What the table shows:

  • Speed does not depend on the number of options in any way you will notice. A decision touches one row per word or character pattern in the message, whatever the size of the table. Per-decision time stayed between 7.1 and 10.7 µs in Python with the C core.
  • Size is roughly patterns × options bytes. Each learned pattern stores one byte per option, plus a 4-byte key. More options, or more varied wording, means a bigger table. With 150 options and no budget, the table was 3.6 MB.
  • A size budget is nearly free. With max_mb=1, the same 150-option table was 1.00 MB and certified exactly the same share (94.4% vs 94.4% without a budget). Most patterns carry almost no weight; training keeps the informative ones and refits on them.
  • Training time grows with options × patterns. It is the slowest part of the system, and the reason budgets matter at scale. The largest run, 500 options with a 4 MB budget (5.0 MB, 57.3% certified), took 21 minutes.

Does the table grow over time?#

Each train() builds a new table from the log and replaces the old one. So the table's size follows the vocabulary of your logged traffic and the number of options. It does not follow how long you have been running.

Size grows when:

  • your users bring new wording (new products, new phrasings, new languages);
  • you add options.

It stops growing once the vocabulary settles, and max_mb caps it either way. The log does keep growing: one line per LLM answer. Rotate or trim it as you would any log. A few tens of thousands of recent answers per question are plenty to train on.

Recommendations#

Options per question Suggested set-up
up to ~100 defaults; tables are small
~100–400 max_mb between 1 and 4; log several thousand answers before expecting a large certified share
~400–1,024 max_mb 4–16; train on a machine with a few GB of RAM; expect training to take tens of minutes
more than 1,024 split into two questions, coarse first (team), fine second (intent within a team)

A two-level split often certifies more than one huge question. A coarse question with a few options certifies early, and each fine question only has to tell a few dozen intents apart.

Memory#

Training holds a weight matrix of options × patterns in memory. Above about 10 million weights, shad0w keeps a shorter optimiser history, and with a max_mb budget far below the vocabulary it keeps only the most frequent patterns before fitting. Both keep memory bounded on a laptop. Serving needs only the table itself.

Many questions#

Each question is its own table and its own certificate. Ten questions of 50 options each are ten small, fast tables, not one large one. Metrics can be shared so they appear on one dashboard.
