The proxy: zero code changes#

shad0w proxy sits between your app and any OpenAI-compatible API. Your code keeps using its OpenAI SDK. Only the base_url changes.

1. Start it#

pip install shad0wllm
shad0w proxy --upstream https://api.openai.com/v1

shad0w proxy on http://127.0.0.1:8010/v1  ->  https://api.openai.com/v1
  dashboard http://127.0.0.1:8010/   metrics http://127.0.0.1:8010/metrics   data /home/you/app/shad0w

The upstream can be OpenAI, Groq, Together, OpenRouter, Mistral, a LiteLLM proxy, Ollama (http://localhost:11434/v1), vLLM or anything else that speaks the chat completions API.

2. Point your client at it#

from openai import OpenAI
client = OpenAI(base_url="http://localhost:8010/v1")

const client = new OpenAI({ baseURL: "http://localhost:8010/v1" });

Your API key is forwarded to the upstream as usual. To keep the key in the proxy instead, use --api-key-env OPENAI_API_KEY.

3. Mark which calls are decisions#

Using the OpenAI Decisions API or a System One model (Jev, Kev, Laya)? Nothing to mark. Requests to /v1/decisions and /v1/systemone already name each question and list its answers, so the proxy recognises them as they are. See Decisions API & System One.

For chat completions, pick whichever is easiest:

# a header
client.chat.completions.create(model="gpt-6-luna", messages=msgs, extra_headers={"X-Shad0w-Question": "intent"})

# a model name: "shad0w/<question>" (the upstream model comes from --model, or "shad0w/intent@gpt-6-luna")
client.chat.completions.create(model="shad0w/intent@gpt-6-luna", messages=msgs)

# a forced tool whose parameters hold exactly one enum: the tool's name is the question
client.chat.completions.create(model="gpt-6-luna", messages=msgs,
    tools=[{"type": "function", "function": {"name": "intent", "parameters": {"type": "object",
        "properties": {"intent": {"type": "string", "enum": ["refund", "lost_card", "balance", "other"]}}}}}],
    tool_choice={"type": "function", "function": {"name": "intent"}})

How each request shape is recognised is set by --capture (or capture in Configuration):

Capture Recognises Default
header the X-Shad0w-Question: <name> header on
model model="shad0w/<name>" or "shad0w/<name>@<upstream model>" on
tools a forced tool (or the only tool) with exactly one enum parameter; the table answer comes back as a tool_calls message on
decisions POST /v1/decisions and POST /v1/systemone on
json_schema any response_format JSON schema with a name; the name is the question off: turn on with --capture json_schema

json_schema is off by default because many apps use named schemas for things that are not decisions. Turning it on means every such request is treated as one.

Where the options come from, in order: a trained table, --schema, the request's own enum (JSON schema or tool parameter), or an X-Shad0w-Options: refund,lost_card,balance,other header.

The text shad0w learns from is the last user message. Put the thing to classify there and keep instructions in the system message.

Everything else (unmarked chat, embeddings, image calls) is forwarded untouched.

What happens to a decision#

Situation What the proxy does
No trained table yet Forwards to the upstream, returns its reply untouched, logs the answer to shad0w/<question>/log.jsonl
Table certified for this text Answers itself in microseconds with a normal chat.completion
Table not sure Forwards, returns the reply, logs the answer (training data for next time)
Upstream error Returns the upstream's error as-is

A table answer is shaped like the request asked:

  • plain text: the option name;
  • JSON object mode: {"intent": "lost_card"};
  • your JSON schema: your field name;
  • a forced tool: a tool_calls message with finish_reason: "tool_calls";
  • stream: true: server-sent events, for text and tool calls;
  • /v1/decisions and /v1/systemone: the same JSON shape the upstream would return.

It carries an extra shad0w field, plus the headers x-shad0w-source: table (or mixed / teacher on the decision endpoints), x-shad0w-confidence and x-shad0w-latency-us.

4. Train#

shad0w stats --log shad0w/intent/log.jsonl        # ready yet?
shad0w train --dir shad0w --question intent       # the running proxy picks the new table up within a second

Or let the proxy do it: shad0w proxy --upstream ... --auto-train 1000 retrains every 1,000 new answers. Training needs pip install "shad0wllm[compile]".

Options#

Every flag can also come from shad0w.toml or a SHAD0W_* variable; see Configuration. A [questions.<name>] section sets values for one question.

Flag Default What it does
--upstream https://api.openai.com/v1 the real API
--dir shad0w logs and tables live in <dir>/<question>/
--bundle Q=PATH use the table at PATH for question Q (repeatable)
--model upstream model for model="shad0w/<question>"
--api-key-env send this env var as the upstream key instead of the client's
--capture header,model,tools,decisions which request shapes count as decisions (see above)
--mode serve serve, shadow (always return the LLM's answer, count what the table would have done), off
--canary 1 share of certified answers the table may serve, 0 to 1
--never-serve comma-separated labels that always go upstream
--min-confidence a confidence floor on top of the certificate (only makes serving stricter)
--audit-rate 0.01 share of decisions spot-checked against the upstream in the background
--auto-train off retrain a question every N new answers
--alpha 0.05 certified disagreement bound for training
--delta 0.1 certificate failure probability
--min-rows 1000 logged answers needed before auto-train runs
--timeout 120 upstream timeout in seconds
--trace JSON Lines file receiving every decision
--cost-per-call your cost per LLM call, to show money saved on the dashboard
--llm-latency-ms LLM latency to assume until one is measured, to show time saved
--schema a schema.json naming each question's options
--no-text keep request text off the dashboard
--config ./shad0w.toml path to a config file
--host, --port 127.0.0.1, 8010 where the proxy listens

The dashboard at / includes a Playground: type a text, pick a question, and see the table's answer, its confidence against the threshold, and why; with --model set, also ask the upstream LLM for the same text and compare the two answers side by side.

The proxy has no authentication of its own. Keep it on localhost or inside your network.
