Troubleshooting#

Start with shad0w doctor. It checks the things that most often go wrong and prints one line each:

shad0w doctor --bundle shad0w/intent/bundle --log shad0w/intent/log.jsonl --llm openai/gpt-6-luna --upstream https://api.openai.com/v1

[ok] is fine, [--] is a warning, [!!] is a problem. It exits 1 when any [!!] line is printed, so it also works in CI.

What each doctor line means#

Line When it is not [ok] Fix
Python — shad0w supports Python 3.10 to 3.13.
C core numpy fallback (same answers, slower) Install from a wheel (pip install shad0wllm), or build it from source with a C compiler (xcode-select --install on macOS, build-essential on Linux). Answers are identical either way.
training deps (scipy, scikit-learn) missing [...] pip install "shad0wllm[compile]". Serving needs only numpy; training needs these. Add [torch] for faster training on large logs.
torch (optional, faster training) [--] Optional. Training falls back to scipy, which is slower on large logs. pip install "shad0wllm[torch]" to add it.
TOML config reader pip install tomli Only on Python 3.10, and only if you use shad0w.toml.
Node (JavaScript package) not found Only needed for the npm package and its tests.
config [!!] with a message shad0w.toml or a SHAD0W_* variable has an invalid value, for example mode = "on". The message names the setting. shad0w config shows every value and where it came from.
provider API key [!!] ... is not set Export the variable it names (for example OPENAI_API_KEY), or pass api_key= in code. Local providers (ollama, vllm, lmstudio, systemone) need none.
upstream reachable [!!] The proxy's --upstream URL cannot be reached. Check the URL ends in /v1 and the server is running. An HTTP error such as 401 still counts as reachable.
bundle question certifies nothing (threshold inf) The table never reached α on held-out answers, so it serves nothing. See "The table answers nothing" below.
certificate.json missing The bundle was copied without its certificate, or built by hand. Run shad0w train (or shad0w certify) again.
log need 1,000 Not enough logged answers yet. Keep running, or lower min_rows for an experiment (100 is the hard minimum).

Messages from the command line#

The CLI prints one line starting with shad0w: instead of a traceback, and exits with code 2.

Message Meaning
no bundle at ... (expected manifest.json; run shad0w train first) The path is wrong, or nothing has been trained yet.
nothing logged yet at ... shad0w stats / train found no log file. With decision() the default log is shad0w/<question>/log.jsonl, relative to where your program runs.
sklearn is not installed; training needs: pip install "shad0wllm[compile]" Training dependencies are missing.
not enough yet: need 1,000 (--min-rows to override; 100 is the hard minimum) shad0w train exits 1 with this.
...kept the old bundle (drop --gate to replace) shad0w train --gate found the new table worse than the current one (under 80% of its certified share) and kept the old one. Exit code 3.
config file ... not found SHAD0W_CONFIG or --config points at a missing file.
mode must be one of ('serve', 'shadow', 'off') and similar An invalid setting; the message names it.

The table answers nothing, or very little#

The certificate only lets the table serve answers it is sure enough of to stay within α. A low share is the certificate doing its job. Common causes:

  • Too few answers. Below about 1,000 per question, the threshold has to be strict. Log more and retrain; the share usually grows with the log.
  • Too many options for the data. With 150 labels and 1,000 rows, most labels have a handful of examples. Log more, or merge rare labels into other.
  • The decision depends on meaning the words don't carry. Sentiment, sarcasm and anything needing reasoning or world knowledge stay hard for a word-level table. shad0w then correctly sends nearly everything to your LLM. See Limits.
  • Your LLM is inconsistent. If it gives different answers to near-identical inputs, no table can agree with it reliably. Check with temperature=0 and a fixed prompt.
  • α is very strict. Try shad0w train --alpha 0.05 and compare the printed share with α 0.02.

shad0w try --bundle ... "some text" shows the table's answer, its confidence, the threshold, and why it deferred.

The teacher fails#

Error Fix
TeacherError: ... replied '...', which matches none of [...] The LLM answered outside your options. Nothing is logged for that call. A few are normal; many mean the prompt or model needs attention: add an other option, describe each option, or use a larger model.
TeacherError: ... HTTP 401 / 403 Wrong or missing API key.
TeacherError: ... HTTP 404 Wrong base_url or model name. For systemone/, the server must implement /v1/systemone; for openai-decisions/, /v1/decisions.
cannot reach http://... The server is down or the URL is wrong. Retries with back-off come first; this is the final error.
unknown provider; pass base_url=... llm="name/model" where name is not a built-in preset. Pass base_url= for any OpenAI-compatible server.

Drift#

Answers flagged drift go to your LLM. The drift guard compares how often the table is unsure on recent traffic (the last drift_window decisions) with how often it was unsure at calibration. When the gap exceeds drift_margin, it raises the flag. It clears by itself when traffic looks familiar again. If it stays raised, your traffic changed: retrain on the new log. Adjust drift_window and drift_margin in Configuration if it is too sensitive for your traffic.

Bursty traffic can trip it even when the overall mix is unchanged. A long run of one hard intent (for example many "card not working" messages during an outage) fills the window with low-confidence answers. In our BANKING77 test the guard stayed silent on shuffled traffic but raised during a long run of one intent, then cleared. If your traffic comes in bursts like that and you prefer to keep serving, raise drift_window (say to 2000) so one burst is a smaller part of the window.

Yes/no questions#

Yes/no answers are stored as booleans. Logs written by shad0w 0.2 through the proxy may hold the strings "yes" and "no"; 0.3 reads them correctly (0.2 learned every one of them as "yes": retrain any yes/no bundle made with 0.2 through the proxy).

The proxy forwards everything#

Symptom Cause and fix
Calls carry no x-shad0w-source header The proxy did not see a decision. Mark it with the X-Shad0w-Question header, a shad0w/<question> model name, a forced tool with one enum parameter, or use /v1/decisions / /v1/systemone. A plain named json_schema is no longer captured by default: add --capture json_schema.
x-shad0w-source: teacher on every call No bundle yet for that question, or it certifies nothing. shad0w stats --url http://localhost:8010 shows each question's state; shad0w train --dir shad0w builds bundles from the proxy's logs, and the proxy picks them up within a second.
A tool call comes back as text The request offered several tools without forcing one, or the tool's parameters hold more than one enum. Force the tool with tool_choice, or use the header.
Multi-question /v1/decisions calls still reach OpenAI Only the questions the table can answer are removed from the upstream request; score questions always go upstream.

"cannot import name 'version' from 'shad0w'"#

You ran python -m shad0w ... from a folder that holds the shad0w/ data folder (where shad0w.decision() keeps its logs and tables by default), with shad0w installed in editable mode (pip install -e). Python then imports the data folder instead of the package. Use the shad0w command instead of python -m shad0w, run from another folder, or pick another data folder with folder= or SHAD0W_FOLDER. A normal pip install shad0wllm is not affected.

pip times out#

Some company networks point pip at an internal mirror that is slow or incomplete. Install from the public index for this one command:

PIP_INDEX_URL=https://pypi.org/simple pip install "shad0wllm[compile]"

Still stuck#

Run with SHAD0W_LOG=debug to print one line per decision (question, answer, source, confidence, flag, latency), and open an issue with that output and shad0w doctor's.
